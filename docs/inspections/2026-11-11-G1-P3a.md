## 2. State transitions

**Consultation:**
- **Doctor abort:** `IN_PROGRESS → ABORTED`. Before the transaction, MRS must confirm nothing is signed or finalized.
- **Admin abort:**
  - `IN_PROGRESS → ABORTED`, under the same signed-items rule.
  - `FINALIZING → ABORTED` only when MRS has not finalized: checkpoint `FINALIZING_ENTERED` **and** MRS `finalized=false`. The finish operation then moves to the new terminal checkpoint `ABORTED` and is never claimed again.
- **Never:** `COMPLETED → anything`, and no un-finalization.

**Appointment** (new exits from `IN_PROGRESS`, only through the abort path):

| Reason | Appointment | Reservation |
|---|---|---|
| `PATIENT_ABSENT` « Patient absent » | `NO_SHOW` (keeps `started_at`) | released |
| `PATIENT_LEFT` « Patient parti avant la fin » | `CANCELLED` (actor DOCTOR, or SYSTEM for an admin abort; code `CONSULTATION_ABORTED_PATIENT_LEFT`) | released |
| `STARTED_BY_MISTAKE` « Démarrée par erreur » / `TECHNICAL_ISSUE` « Problème technique » | `CONFIRMED` if slot start ≥ now, `started_at` cleared; otherwise `CANCELLED` | kept if `CONFIRMED`, released otherwise |

The slot is compared as instants from `TimeProvider`. That is the same instant in Africa/Tunis; the boundary counts as « not passed ».

**MRS care context:** `ACTIVE → CLOSED (close_reason=ABORTED)` applies the abort side effects. An aborted context never reopens and never completes.

## 3. Backend (Spring)

### 3.1 Abort
`POST /api/v1/doctor/consultations/{id}/abort`
- Role DOCTOR, owner only, `Idempotency-Key` (command receipts, scope `CONSULTATION_ABORT`).
- Body: `{reason, expectedConsultationVersion}`.
- Returns 200 with the consultation (`status: ABORTED`). A replay with the same key returns the same body, with no new side effects.

**The one transaction:**
1. Lock the consultation; re-check status and version.
2. `Consultation.abort`.
3. The appointment transition, and the reservation release when needed.
4. Audit `CONSULTATION_ABORTED`: consultationId, sourceType, sourceId, reasonCode, appointmentStatus, outcome, occurredAt, version.
5. Care-context close enqueued with `close_reason=ABORTED`.
6. Realtime `CONSULTATION_UPDATED` to the doctor.
7. Receipt completed.

The local medical-access mirror becomes `REVOKED`; the real grant revocation is MRS's.

**Errors:**

| Status | Code | When |
|---|---|---|
| 409 | `CONSULTATION_HAS_SIGNED_ITEMS` | MRS reports something signed or finalized |
| 409 | `CONSULTATION_NOT_IN_PROGRESS` | not IN_PROGRESS |
| 409 | `CONSULTATION_VERSION_CONFLICT` | version mismatch |
| 404 | `CONSULTATION_NOT_FOUND` | another doctor's consultation |
| 409 | `CONSULTATION_ABORT_NOT_SUPPORTED` | §10.1 / §10.3 |
| 503 | `MRS_UNAVAILABLE` + `Retry-After: 30` | MRS can't answer; we never abort blind |
| 400 | `VALIDATION_FAILED` | bad body |
| 409 | `IDEMPOTENCY_KEY_REUSED` | as today: 409, not 400 |

### 3.2 Stuck closure
- **Bounded retries:**
  - Settings: `omnicare.consultation.finish.max-attempts=10`, `base-backoff=30s`, `max-backoff=1h`.
  - Backoff is `min(30 s·2^(n−1), 1 h)`.
  - A **permanent** error dead-letters immediately; the 10th transient failure dead-letters too.
- **Dead-letter:**
  - Column `dead_lettered_at` on `consultation_finish_operations`; `claimDue` skips these operations and terminal ones.
  - New table `consultation_finish_dead_letter`: code, permanent flag, attempts, resolution RETRIED/ABORTED with who and the reason text. At most one open row per operation.
- **Alert:**
  - An ERROR log with codes and ids only.
  - A new notification type `ADMIN_CONSULTATION_FINISH_FAILED` (CRITICAL, category ADMIN), with a French template free of medical data, sent through the existing notification outbox to every admin.
  - `ADMIN_DEAD_LETTER` was not reused, because its template says « Une notification a échoué ».
  - The alert is queued after the dead-letter commits. If queuing fails, only a WARN is logged; the dead-letter row stays the source of truth.
- **Admin endpoints** (ADMIN only, also covered by the `/api/v1/admin/**` chain):

  | Route | Body | Allowed | Audit |
  |---|---|---|---|
  | `POST /api/v1/admin/consultations/{id}/finish/retry` | `{reason}`, 10–500 chars; the text is stored only on the dead-letter row | dead-lettered operation only, else 409 `FINISH_NOT_FAILED`. Resets the attempts and schedules it now. | `ADMIN_CONSULTATION_FINISH_RETRIED` |
  | `POST /api/v1/admin/consultations/{id}/abort` | `{reason}` = one of the 4 codes | see §2 | `CONSULTATION_ABORTED` + `ADMIN_CONSULTATION_ABORTED` |

  Admin abort refusals:
  - 409 `CONSULTATION_ALREADY_FINALIZED` when MRS has finalized (only retry is possible then);
  - 409 `CONSULTATION_HAS_SIGNED_ITEMS` (§10.2);
  - 409 `FINISH_IN_PROGRESS` when a reconciler attempt holds the operation's lease.
- **Index:** `uq_consultation_doctor_active` is recreated `WHERE status='IN_PROGRESS'` (same name; a subset of the old index, so it is safe on existing data; with rollback). The Java check in `ConsultationStartWriter` was changed the same way. A doctor with a FINALIZING consultation can start another one.

### 3.3 Resume (S5) and `finishState`
- `GET /doctor/consultations/{id}` returns `finishState`: `RUNNING` (a closure is in progress or retrying), `FAILED` (dead-lettered) or `null`. No technical detail.
- `POST …/finish` with `expectedClinicalRecordVersion` omitted or null:
  - allowed only when this doctor's finish operation exists; it resumes with the **captured** versions, with no readiness call and no clinical-record read;
  - null without an operation → 400;
  - dead-lettered → 409 `CONSULTATION_FINISH_FAILED`; `advance()` is never re-run for it.

  This removes the dependency on the clinical-record GET, which is refused in FINALIZING (inspection §1.8).

### 3.4 Legacy routes
- `PATCH /api/v1/appointments/{id}/start` and `/complete` → **410** problem body `errorCode: ENDPOINT_RETIRED` (still DOCTOR-only).
- `BookingService.start/complete` were removed. `BookingServiceStartCompleteTest`, which codified the bypass, now asserts they are gone.
- `PATCH /{id}/cancel` (doctor/patient, CONFIRMED only) is unchanged (§10.9).

### 3.5 Migrations
Liquibase `05-appointment/0518-g1p3a-consultation-lifecycle-safety.yaml`, four changesets, each with a rollback:
1. The index on IN_PROGRESS only.
2. The finish dead-letter:
   - `dead_lettered_at`;
   - checkpoint `ABORTED`, with the constraint « ABORTED ⇒ no MRS finalization receipt »;
   - a narrowed reconcile index;
   - the dead-letter table.
3. `close_reason` on the care-context projection state and outbox.
4. The notification template.

The rollback of changeset 1 fails safely (unique violation, nothing deleted) if a doctor meanwhile has one IN_PROGRESS and one FINALIZING consultation.

## 4. MRS
- **Lifecycle state:** `GET /internal/mrs/patients/{p}/consultations/{c}/lifecycle-state` returns `{finalized, has_signed_items}`.
  - SYSTEM role only, the same guard as `completion-cleanup`; read-only.
  - `has_signed_items` = a prescription signature, or a FINALIZED order, or a FINALIZED artifact.
- **Abort applied:** on the care-context `PUT` with `close_reason: "ABORTED"` (migration `000040_care_context_close_reason`), one transaction, audited `CONSULTATION_ABORT_APPLIED`:
  1. Patient row locked (the same fence as finalization).
  2. Refused with 409 `CONSULTATION_ALREADY_FINALIZED` if a finalization exists: never un-finalize. Spring treats this as a permanent projection failure.
  3. DRAFT orders and DRAFT artifacts deleted through the 2b `DeleteDraft`.
  4. The unsigned prescription draft marked DELETED.
  5. ACTIVE grants of the consultation revoked (`CONSULTATION_ABORTED`) with their view sessions. The revocation code is now shared with completion cleanup.
  6. Context `CLOSED` with `close_reason='ABORTED'`.

  **The note is kept** (never deleted). Replays are no-ops.
- **Hidden everywhere:** aborted consultations are excluded from:
  - the doctor chart list, page, detail and medications (P2d);
  - the workspace summaries and current medications;
  - `completion.History`;
  - the patient medications route;
  - `GET /records/{recordID}` for the note and the prescription.

  The current-record read was already refused for a closed context.

## 5. Transient vs permanent finish errors (`FinishFailureClassification`)

**Permanent** (dead-letter immediately):
- `CONSULTATION_NOT_READY_TO_FINISH` (validation)
- `CLINICAL_RECORD_VERSION_CONFLICT`, `CONSULTATION_VERSION_CONFLICT`
- `MEDICAL_SUMMARY_UPDATE_NOT_ALLOWED` (custody changed, P2a §9.8)
- `PROFESSIONAL_NOT_ELIGIBLE` (MRS `ACCESS_DENIED`, also returned when the care context is closed)
- `IDEMPOTENCY_KEY_REUSED`
- `CONSULTATION_ABORTED`
- `CARE_CONTEXT_CLOSE_FAILED` (the CLOSED projection itself dead-lettered)
- inconsistent source: `APPOINTMENT_NOT_COMPLETABLE`, `APPOINTMENT_RESERVATION_MISSING`, `RESERVATION_NOT_RELEASABLE`, `URGENT_SOURCE_FINISH_DEFERRED`, `CONSULTATION_NOT_COMPLETABLE`

**Transient** (backoff; dead-letter on the 10th failure):
- `MRS_UNAVAILABLE`: also every 5xx and every MRS code Spring does not map, see §10.8
- `FINISH_IN_PROGRESS`, `MRS_CONTEXT_PENDING`
- `CARE_CONTEXT_CLOSE_PENDING`: waiting for the close acknowledgement counts as an attempt but is not audited as a failure
- `FINISH_RETRY_REQUIRED`, `FINISH_RECONCILIATION_REQUIRED`
- any unknown code (bounded)

## 6. Angular

### 6.1 Abort
- **Header action « Annuler la consultation »:** ghost button in the error colour.
  - Shown only when the consultation is IN_PROGRESS and loaded, nothing is signed (prescription, validated order or signed document; the server enforces the same rule), and no « Terminer » is running.
  - Otherwise there is no button.
- **NG-ZORRO modal « Annuler la consultation ? »:** NG-ZORRO radio list of the 4 reasons, each with its consequence in one line.
  - « Le rendez-vous sera marqué absent. »
  - « Le rendez-vous sera annulé. »
  - « Le rendez-vous redevient confirmé. » or « … annulé (son horaire est passé). », from the appointment's start time. If that time is unknown, one sentence covers both cases.
  - A note: unsigned drafts are discarded and the note is kept but not shown in the record.
  - Buttons « Revenir » / « Annuler la consultation » (destructive, disabled until a reason is chosen).
- **On success:** autosave stops, and the page shows « Consultation annulée » with « Retour à l'accueil ». The header tag reads « Annulée » and the active consultation is refreshed. A reloaded aborted consultation shows the same state (it used to say « Consultation interrompue »).
- **Errors:** mapped by code to French: `CONSULTATION_HAS_SIGNED_ITEMS`, `CONSULTATION_NOT_IN_PROGRESS`, `CONSULTATION_ABORT_NOT_SUPPORTED`, `MRS_UNAVAILABLE`, conflicts. The server text is never shown. The same `Idempotency-Key` is kept after an ambiguous failure (network or 5xx).

### 6.2 FINALIZING after a reload
- **The closure failed** (`finishState: FAILED`): the page shows « La clôture n'a pas pu aboutir. Le support a été prévenu. » and « Retour à l'accueil ». There is no polling and no resume, and autosave stops. Polling also stops as soon as the server reports FAILED.
- **Otherwise:** « Clôture en cours… » polls for 2 minutes, then shows « La clôture prend plus de temps que prévu. » and « **Reprendre la clôture** ».
  - It sends `finish` with the current consultation version and **no** clinical version (§3.3): no clinical-record GET, no readiness call.
  - It receives 200 COMPLETED → « Consultation terminée ».
  - 409 `FINISH_IN_PROGRESS` / 503 pending → polling again.
  - 409 `CONSULTATION_FINISH_FAILED` → re-reads the consultation, which gives the failed state.

### 6.3 Legacy callers
- `AppointmentApiService.startAppointment / completeAppointment / cancelAppointment` were removed. The last was the duplicate legacy PATCH cancel, with no caller left; the versioned POST cancel stays.
- The Accueil appointment-details dialog lost its « Commencer » / « Terminer » buttons (which called the retired routes) and keeps « Fermer ». Starting goes through « Démarrer la consultation ».
- `npm run check:ui-boundaries` now fails if a `PATCH …/start` or `…/complete` call appears in `src/app`.

## 10. Points reported (not covered by the prompt or the ADRs; please decide)

1. **Urgent sources (URGENT_CABINET / URGENT_HOME):** decision 1 only defines the appointment effect, so abort answers 409 `CONSULTATION_ABORT_NOT_SUPPORTED` for these (doctor and admin). No semantics were invented.
2. **Admin abort vs decision 2.** I applied the signed-items refusal to admins too, because decision 2 doesn't exempt them. But a stuck FINALIZING consultation almost always has a signed prescription, so in practice the admin can only **retry** it. Should an admin be allowed to abort a stuck closure that has signed items, and what happens to the signed prescription then?
3. **Inconsistent source.** If the appointment is no longer IN_PROGRESS (e.g. legacy-completed while the consultation stayed IN_PROGRESS) or its reservation isn't ACTIVE, abort is refused (409 + WARN `ABORT_SOURCE_INCONSISTENT`). Such a consultation can be neither aborted nor finished, so it needs a rule.
4. **No patient-facing notification on abort.** No `APPOINTMENT_CANCELLED` / no-show event goes to an OmniCare patient; the app sees the new status on refresh. Should the patient be told?
5. **ADR-003 #17:** the code follows the CTO rule (1 open = IN_PROGRESS only), and the ADR still says « at most 2 ». The architect writes the amendment. `GET /active` returns the newest when one is FINALIZING and one IN_PROGRESS.
6. **Residual race.** Admin abort refuses while a reconciler attempt holds the lease (`FINISH_IN_PROGRESS`), but the doctor's own synchronous « Terminer » takes no lease. If MRS finalizes in that window, Spring would show ABORTED while MRS refuses the abort (`CONSULTATION_ALREADY_FINALIZED`, permanent, logged). The record is never un-finalized, but the mismatch needs a manual follow-up. This is very unlikely, since admin abort is rare and happens on stuck operations.
7. **COMPLETED with a dead-lettered later step** (e.g. the care-context close failed): `finishState: FAILED`, and the doctor page shows « Consultation terminée », because the status decides. The admin retry finishes the remaining steps.
8. **Unmapped MRS errors during finalize** (`IDEMPOTENCY_CONFLICT`, `SINGLETON_SERIES_AMBIGUOUS`, a decode 500, `PATIENT_NOT_ACTIVE` 500) arrive as `MRS_UNAVAILABLE`, so they retry as transient and dead-letter after 10 attempts rather than at once.
9. **Legacy `PATCH /appointments/{id}/cancel`** still exists (the prompt only retires start and complete). The patient web portal (`features/patient/patient-api.service.ts:72`) still calls it; the doctor side no longer does. Retire it too?
10. **MRS abort details:**
    - every DRAFT artifact is discarded, whatever its type (the doctor's 2b discard only allows certificates);
    - a prescription draft that **corrects** an already signed prescription is kept (2b rule);
    - no sharing-policy lock on abort (the reads exclude the consultation anyway);
    - the by-id record read refuses an aborted note for every role, including SYSTEM;
    - medications from an aborted consultation are hidden. With the Spring rule nothing can be signed there, but MRS alone doesn't block it.
11. **Audit content:** `CONSULTATION_ABORT_APPLIED` carries ids only. The MRS audit model has no field for counts (orders/certificates discarded, grants revoked), so they are computed but not stored.
12. **No admin UI.** The admin retry/abort exist as API endpoints only. A support screen is not in this prompt.
13. **Scratch database left by the MRS helper:** `omnicare_mrs_p3a_test` on your local Homebrew Postgres, kept for reruns. Drop it with `dropdb -h localhost omnicare_mrs_p3a_test` when you don't need it.
